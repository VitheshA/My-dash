Live market data with yfinance

yfinance gives you two doors into Yahoo Finance. yf.download(tickers, ...) returns price history — a date-indexed DataFrame of OHLCV, and it can fetch many tickers in one call. yf.Ticker("AAPL") returns a company object whose .info dict holds snapshot fundamentals: market cap, trailing P/E, margins, dividend yield. MODULE 03watch · ~15 m + read

Time series: DatetimeIndex, slicing & rolling windows

Price data is special because its index means something: order and spacing carry information. Once a DataFrame has a proper DatetimeIndex (yfinance gives you one for free), three superpowers switch on. Date slicing: df.loc["2024":] just works. Resampling: df.resample("ME").last() converts daily prices to month-end prices — you will use this exact line in the momentum backtest. Rolling windows: df["Close"].rolling(50).mean() computes a 50-day moving average, the workhorse of trend measurement.

The classic trend signal is the golden cross: the 50-day average crossing above the 200-day average (bullish); crossing below is a death cross. Whether it predicts anything is debated — but detecting a crossover in code teaches you rolling, shift, and boolean logic in one shot, which is exactly the toolkit backtesting needs.

The mental model that unlocks all of pandas: a Series is never bare values — it's values stapled to labels (the index). Comparing two columns pairs them by label and returns a new labeled True/False Series; putting that Series in brackets keeps the True-labeled rows; .index just reads the labels back out. Every pandas operation is "align by label, act, return a new labeled thing." And the crossover idea in one sentence: "is above" can be true 300 days in a row — a cross is only the day the answer changes — which is exactly what combining today's condition with ~ of its shifted sibling encodes.

MODULE 04watch · ~1 h

NumPy under the hood: why there are no loops

Every time pandas compared two whole columns for you in one line, NumPy was the thing actually doing it. NumPy's one idea: the array — a block of numbers of a single type, stored contiguously, so math on the entire block runs in compiled C instead of a Python loop. That's called vectorization, and it's why array math is both hundreds of times faster than looping and harder to get wrong — there's no bookkeeping for you to fumble. pandas is NumPy wearing labels; statsmodels and scikit-learn are NumPy wearing math. Learn the substrate once and every library above it makes sense.

From here forward the track adopts the professional rule: zero for loops over rows of data. If you catch yourself writing one, stop and ask which array operation replaces it. (Loops over tickers making API calls are fine — that's I/O, not math.)

MODULE 05watch · ~15 m + short read

Returns math: prices lie, returns compare

A $900 stock moving $9 and a $30 stock moving $3 had very different days — which is why quants convert prices to returns immediately. df["Close"].pct_change() gives simple daily returns. Chain them with a cumulative product, (1 + r).cumprod(), and you get the growth of $1 — the fair way to compare any two assets on one chart regardless of price level.

Two more tools finish the kit. Annualization: volatility scales with the square root of time, so annual vol ≈ daily-return std × √252 (252 trading days). CAGR: (end_value / start_value) ** (1 / years) - 1 — the single growth rate that compounds to the same endpoint. You'll also meet log returns (np.log(p / p.shift(1))) which add across time instead of compounding; know they exist, use simple returns for now.

Two roads to the same returns. pandas: df["Close"].pct_change() — labels do the day-pairing for you. Raw NumPy: closes[1:] / closes[:-1] - 1 — closes[1:] is "today," closes[:-1] is "yesterday," and element-wise division pairs them by position. It's shift(1) in position clothing, using exactly the slicing you drilled in Module 04. Both roads must give identical numbers; the second stretch below makes you prove it.

Distributions & fat tails: what returns actually look like

Before you can score stocks with z-scores (next module) or test strategies with t-tests (Module 17), you need the idea underneath both: the distribution — the shape traced out when you histogram every daily return. The most famous shape is the normal distribution, the bell curve, fully described by just a mean and a standard deviation. Under a normal curve, ±2σ covers ~95% of days and a ±3σ day should happen roughly once a year.

Here's the punchline this module exists for: market returns are not normal. Real return histograms have fat tails — extreme days occur far more often than the bell curve permits. October 1987 was a ~20σ event; under normality it shouldn't happen in the lifetime of the universe. Quants still use the normal as scaffolding (z-scores, Sharpe, regression all lean on it) — but they use it knowing exactly where it lies. After today, so will you. Vocabulary you'll compute: skew (is the tail longer on one side?) and kurtosis (how fat are the tails?).

Normalize & rank: making metrics comparable

You can't average a P/E of 18 with an ROE of 0.22 — different units, different scales, and P/E is better low while ROE is better high. Normalization fixes all three problems. The two workhorses:

  • Percentile rank — df["roe"].rank(pct=True) maps every value to 0–1 by position. Robust, ignores outliers, loses magnitude.
  • Z-score — (x - x.mean()) / x.std() — "how many standard deviations from average." Keeps magnitude, but one insane outlier drags the whole scale, so quants first winsorize: clip extremes to, say, the 1st/99th percentile with x.clip(x.quantile(.01), x.quantile(.99)).

Two finishing moves. Flip lower-is-better metrics (negate the z-score, or rank ascending) so that high always means good before combining anything. And compare within sectors when the metric's "normal" differs by industry — a utility and a software firm shouldn't share a P/E scale. groupby("sector")["pe"].transform(zscore) is the idiom; transform keeps the original row shape, which is exactly why it exists.

Try writing zscore() yourself from the description above — then reveal the reference implementation
def zscore(s):
    s = s.clip(s.quantile(0.01), s.quantile(0.99))   # winsorize
    return (s - s.mean()) / s.std()

uni["roe_z_sector"] = uni.groupby("sector")["roe"].transform(zscore)

Backtests & the three lies they tell

A backtest replays history under a rule: each month, hold X; measure what the portfolio would have been worth. Mechanically it's things you own already — resample to month-end, pct_change, cumprod. The hard part is that backtests default to lying, in three specific ways you must be able to name in an interview:

  • Lookahead bias — the rule uses information not yet available at decision time. Classic tell: computing this month's signal and this month's return from the same row. The fix is one shift(1): decide on last month's data, earn this month's return.
  • Survivorship bias — testing on today's index members means every bankrupt or delisted loser was quietly removed before you started. Results inflate. We accept this bias in our student project and disclose it in the README — knowing your data's flaw beats pretending it away.
  • Cost blindness — monthly rebalancing churns the book; at even ~10bps a trade, ignored costs flatter the strategy. We'll apply a simple haircut per rebalance.

The 12-1 momentum signal

Momentum is the most stubborn anomaly in the academic record: recent winners tend to keep winning over 3–12 month horizons. The standard signal since Jegadeesh & Titman (1993) is 12-1 momentum — the return from 12 months ago to 1 month ago. The most recent month is deliberately excluded because stocks show short-term reversal at the one-month horizon; including it degrades the signal. Each month-end you rank the universe by this number and hold the top N. That's the whole strategy. Resist improving it — the boring lookback has survived thirty years of people trying.

In pandas, on a month-end price frame, the signal is one line: mom = monthly.pct_change(11).shift(1) — 11 monthly periods of return, shifted so that the value sitting on July 31 was fully knowable on July 31. Say out loud what that shift is protecting you from before you use it.

Skill or luck? Hypothesis testing before you need it

Your P4 backtest beat SPY (or didn't). The question a professional asks next is brutal and precise: could pure luck have produced this? Hypothesis testing is the machinery for answering it. You assume the boring world — the null hypothesis, "this strategy has no real edge; its true average excess return is zero" — and then ask how surprising your observed result would be if that boring world were true. That surprise level is the p-value: the probability of seeing a result at least this good by chance alone. Small p (convention: < 0.05) lets you say the result is statistically distinguishable from luck. It never proves skill; it only makes luck an uncomfortable explanation.

One more idea, and it's the one that will guard your whole future in this field: test enough random strategies and some will look brilliant. Run 1,000 monkeys, crown the best one, and its track record looks like genius. This is why "each tested variation is a hypothesis" — every tweak-and-rerun of a backtest spends a little of your statistical credibility. Today you build the monkey army and see it with your own eyes.

The regression → ship Project 5

Ordinary least squares (OLS) fits the line that best explains an asset's excess returns using the factors. The equation you're estimating: r − rf = α + β·(Mkt−RF) + s·SMB + h·HML + ε. Abnormal returns: what would have happened anyway?

"NVDA rose 4% after earnings" is meaningless if the whole market rose 3% that day. An event study subtracts the counterfactual. The design has three parts, and the vocabulary matters because it's universal across every finance paper you'll ever read:

  • Estimation window — e.g. trading days −250 to −20 relative to the event: quiet history used to fit a market model, a simple OLS of the stock's daily return on the market's: r = α + β·r_mkt. (Yes — the same regression as Module 18, just daily and one factor.)
  • Event window — e.g. days −5 to +5 around the event.
  • Abnormal return (AR) — actual return minus the model's prediction, each day in the event window. CAR is the running sum of ARs: the cumulative surprise attributable to the event.

Covariance: why portfolio risk isn't an average

Here's the deepest free lunch in finance: a portfolio's return is the weighted average of its parts, but its risk is not. Two volatile assets that zig at different times partially cancel — the whole is calmer than its pieces. The object that captures every pairwise "do they move together?" relationship is the covariance matrix: an N×N grid, variances down the diagonal, co-movements everywhere else. Portfolio variance is then one gorgeous line — w @ cov @ w.T — and understanding why that line works is what the linear-algebra on-ramp below is for. This is where math wave three arrives, with a concrete payoff waiting.

The efficient frontier → ship Project 7, complete the track

Markowitz's 1952 insight — the one the Nobel committee eventually caught up with — is that portfolios live on a map: expected return on one axis, risk on the other. Random weightings scatter into a cloud; the efficient frontier is the cloud's upper-left edge, where no portfolio offers more return for the same risk. Two points on that edge matter most: the minimum-variance portfolio (calmest possible mix) and the maximum-Sharpe portfolio (best return per unit of risk). You'll find them twice — once by brute-force Monte Carlo (20,000 random weight vectors, fully vectorized), once properly with scipy.optimize.minimize — and watching the optimizer land on the edge of your own random cloud is one of the great "oh, it's all real" moments of this track.

Floating point

Orientation
Objective
Understand where numerical error originates and where measurement stops being meaningful.
You already know
Limits, algebraic manipulation.
New
Machine epsilon, catastrophic cancellation.
Read
BOOK
Moler Ch. 1, §1.7 — Floating-Point Arithmetic~10 pp
Why this section: shortest correct treatment of floating point that exists, and every error measurement in this track has a floor set by it.

The mathematics

Computing (1 − cos x)/x² for small x subtracts two numbers agreeing in their leading digits. If cos x carries 16 significant digits and the subtraction destroys 8, you keep 8 digits of signal and 8 of noise — then divide by x² and amplify the noise.

1 − cos x = 2 sin²(x/2)Algebraically identical. Numerically different — no cancellation occurs.
Derive yourself: verify the identity using the double-angle formula. Two lines.
Practice — before the build

  5. Evaluate 1 - cos(x) at x=1e-8. How many correct significant digits survive? Count them.
  6. Sum 1/n for n=1..10⁶ forward, then backward. Which is more accurate, and why?

  8. Find the smallest x where 1 + x != 1. Relate it to problem 1.

Root finding

Orientation
Objective
Learn convergence order and measure it.
You already know
Taylor expansion with remainder (BC).
New
Convergence order as a defined, measurable quantity.
Read
BOOK
Moler Ch. 4, §4.1–4.6 — Zeros and Roots
Why: the simplest setting where convergence order is visible, and the derivation below is the template for every error analysis in this track.

The mathematics — derive by hand before coding

Let r be the root, xₙ your guess, eₙ = r − xₙ. Taylor expand f about xₙ, evaluated at r:

0 = f(r) = f(xₙ) + f′(xₙ)(r − xₙ) + ½ f″(ξ)(r − xₙ)²

Divide by f′(xₙ), substitute Newton's step:

eₙ₊₁ ≈ −½ · [ f″(ξ) / f′(xₙ) ] · eₙ²Error squares each step. That's quadratic convergence — and the f′ in the denominator tells you exactly what breaks it.
Practice
  1. By hand: two bisection steps on x²−2, bracket [1,2]. Write the interval each time.
  2. By hand: two Newton steps on the same from x₀=2.
  3. Implement bisection only. Confirm it matches your hand calculation.
  4. Add an iteration counter. How many iterations to reach 10⁻¹⁰?
  5. Predict first: how many more bisection steps from error 10⁻³ to 10⁻⁶? Verify.
  6. Implement newton. Count iterations to 10⁻¹⁰. Compare.
  7. Run Newton on x^(1/3) from x₀=1. Describe what happens and why the derivation predicts it.
  8. Run Newton on x² (double root at 0). Measure the order. It won't be 2 — explain why using your error formula.
Build
Three root finders numerical/rootfind.py
Spec
bisection, newton, secant — each returns the root and full iteration history.
Experiment
On x²−2, estimate observed order numerically.
Record
Measured p per method. Theory says 1, 2, ≈1.618. Report what you measure regardless.
p ≈ log(eₙ₊₁/eₙ) / log(eₙ/eₙ₋₁)
Stuck? Open hints

Local versus global error

Read
BOOK
Moler §7.10–7.13
Why: before explaining the energy drift you need to know precisely what error means over many steps.

The mathematics

Local truncation error is what one step introduces assuming everything prior was exact. Global error is what you actually have after n steps. The relationship depends on how the method amplifies existing error — which is stability, separate from accuracy. That separation is the investigation.

Practice
  1. Compute the exact solution at each step for the decay problem. Store it.
  2. At each step compute local error — one step from the exact previous value versus the exact current value.
  3. At each step compute global error — your numerical value minus exact.
  4. Plot both against t. Which grows faster?
  5. Sum all local errors to t=1. Compare against global error at t=1. Same? Larger? Smaller?
  6. Repeat with h halved. How does the ratio change?
  7. Do the same for RK4. Is the relationship the same shape?

The mathematics — derive by hand

Apply a method to dy/dt = λy. Every one-step method gives yₙ₊₁ = R(hλ)·yₙ. For Euler:

yₙ₊₁ = (1 + hλ) yₙ  ⟹   R(z) = 1 + z,  z = hλ

High-dimensional integration

The mathematical centerpiece, and the bridge to P4. Three phases: build, scale, explain.

Three things to keep separate

Asymptotic rate. A tensor grid with n points per axis in d dimensions costs N = nᵈ. A rule of order p gives:

tensor grid: error = O(N−p/d)     Monte Carlo: error = O(N−1/2)The grid exponent degrades with dimension. The Monte Carlo exponent doesn't contain d at all.

Constant factors. Rates hide constants. Two methods with the same rate can differ by orders of magnitude at finite N.

Finite-budget performance. What you observe at N = 10⁶ depends on rate and constant and regularity. This is what you measure.

The two integrands — two independent sources of difficulty
A — very smooth
f(x) = exp(−Σᵢxᵢ²) over [−1,1]ᵈ. This factorizes, so the exact value is a product of erf terms — scipy.special.erf gives it in one line. Don't assume you need a different function.

Indicator on an inscribed ball, or a function with a kink. Exact value known analytically.

Three optimizers and a fair budget

Read
PAPER
Kirkpatrick, Gelatt & Vecchi (1983) — "Optimization by Simulated Annealing," Science 220(4598)
First three pages only. Remarkably readable, and it's the original statement of the acceptance criterion.
P(accept) = exp(−Δ / T)As T → 0 this becomes greedy. The cooling schedule is the entire design problem.
Just-in-time prerequisite: gradient descent is Calculus III — the gradient points uphill, you step against it. You already have this.

The budget problem — resolve before running anything

Gradient descent uses derivative information the others don't. Counting raw function evaluations hands it free information and invalidates the comparison. Run both definitions.
Two budget definitions
Budget A — oracle-equivalent
A gradient in d dimensions costs what finite differences would: d + 1 function evaluations. Charge gradient descent (d+1) per step. Standard convention; makes the comparison defensible.
Budget B — wall-clock
Equal seconds per method. Captures implementation cost, which A ignores.
Report
Both. If they disagree, that disagreement is itself a finding — and it's the first thing a reviewer would probe.
Practice
  1. Implement gradient descent with fixed step size. Test on the sphere in 2D.
  2. Predict, then check: what happens with too large a step? Too small?
  3. Run gradient descent on Rastrigin from 20 random starts. What fraction find the global minimum?
  4. Implement random restart — GD from k random starts, keep the best.
  5. Implement the annealing acceptance rule alone. Verify empirically that the acceptance rate matches exp(−Δ/T).
  6. Build full simulated annealing with a geometric cooling schedule.
  7. Count evaluations. For GD in d dimensions, how many function evaluations does one gradient cost?
  8. Instrument all three to report evaluations used under A and wall-clock seconds under B.
Journal: which budget definition you expect to matter more — recorded before you run.
